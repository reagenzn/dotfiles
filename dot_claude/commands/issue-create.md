# Issue 作成ワークフロー

引数: $ARGUMENTS（Issue の概要説明。例: 「ユーザー一覧画面にページネーションを追加」）

## 概要

ユーザーの説明から GitHub Issue を起票する。体裁・ラベル・完了条件を統一し、画面変更がある場合はアスキーアートで UI イメージを含める。

### 基本方針: Issue に全て書く

- 外部ドキュメントへのリンクで済ませず、**Issue 本文に必要な情報を全て記載**する
- Issue だけ読めば実装に着手できる状態を目指す
- 詳細設計レベルの粒度だが、厳密なフォーマット設計書ではなく「実装者が迷わない程度」でOK
  - 影響するファイル・モジュールがわかる
  - API のエンドポイント・リクエスト/レスポンスの形がわかる
  - DB 変更があればカラムと型がわかる
  - 主要な処理フローがわかる
  - エッジケースとエラー時の挙動がわかる

---

## Step 1: ヒアリング

ユーザーの $ARGUMENTS を分析し、不足情報があれば AskUserQuestion で確認する。

確認項目:

- **Issue 種別**: `bug` / `feature` / `improvement` / `chore`
- **対象リポジトリ**: 現在のリポジトリか、他リポか
- **画面変更の有無**: UI に変更があるか
- **優先度**: `priority:high` / `priority:medium` / `priority:low`
- **関連 Issue / PR**: あれば番号

さらに、詳細設計を書くために必要な情報を深掘りする:

- **影響するモジュール・レイヤー**: フロント / バックエンド / DB のどこに触るか
- **API の有無**: 新規 or 既存エンドポイントの変更があるか
- **DB 変更の有無**: テーブル追加・カラム追加があるか
- **主要な処理フロー**: ユーザー操作からレスポンスまでの流れ
- **エッジケース**: 想定されるエラーケースや境界値

ユーザーの $ARGUMENTS とコードベースの調査（Grep / Read）から読み取れる情報は自分で埋める。不足分だけ質問する。

---

## Step 2: ラベルの決定

以下のルールでラベルを自動選定する。

### 種別ラベル（必須・1つ）

| ラベル        | 条件                          |
| ------------- | ----------------------------- |
| `bug`         | 既存機能の不具合              |
| `feature`     | 新機能の追加                  |
| `improvement` | 既存機能の改善・リファクタ    |
| `chore`       | CI/CD、依存関係、設定変更など |

### 優先度ラベル（必須・1つ）

| ラベル            | 条件                               |
| ----------------- | ---------------------------------- |
| `priority:high`   | ブロッカー、本番障害、セキュリティ |
| `priority:medium` | 通常の開発タスク（デフォルト）     |
| `priority:low`    | 改善提案、将来対応でよいもの       |

### スコープラベル（該当すれば付与）

| ラベル     | 条件                            |
| ---------- | ------------------------------- |
| `frontend` | UI / フロントエンド変更         |
| `backend`  | API / サーバーサイド変更        |
| `database` | スキーマ / マイグレーション変更 |
| `infra`    | インフラ / CI/CD 変更           |
| `docs`     | ドキュメントのみの変更          |

---

## Step 3: Issue 本文の作成

以下のテンプレートに従って Issue 本文を生成する。

````markdown
## 概要

<!-- 1〜3文で何をするか / 何が問題かを説明 -->

## 背景・動機

<!-- なぜこの Issue が必要か。ビジネス要件やユーザーの課題を記述 -->

## 画面イメージ

<!-- 画面変更がある場合のみ記載。ない場合はこのセクションを削除 -->

### Before（現状）

```
┌─────────────────────────────────┐
│  Header                         │
├─────────────────────────────────┤
│                                 │
│  （現状の画面をアスキーアートで） │
│                                 │
└─────────────────────────────────┘
```

### After（変更後）

```
┌─────────────────────────────────┐
│  Header                         │
├─────────────────────────────────┤
│                                 │
│  （変更後の画面をアスキーアートで）│
│                                 │
└─────────────────────────────────┘
```

## 詳細設計

### 影響範囲

<!-- 変更対象のファイル・モジュールを列挙 -->

| レイヤー | 対象ファイル / モジュール | 変更内容                      |
| -------- | ------------------------- | ----------------------------- |
| Frontend | `src/components/Xxx.tsx`  | 新規作成 / 修正内容           |
| Backend  | `src/api/xxx.ts`          | エンドポイント追加 / 修正内容 |
| Database | `migrations/xxx.sql`      | テーブル追加 / カラム追加     |

### データ設計

<!-- DB変更がある場合。ない場合は削除 -->

テーブル: `table_name`

| カラム | 型           | 制約     | 説明   |
| ------ | ------------ | -------- | ------ |
| id     | UUID         | PK       | 主キー |
| name   | VARCHAR(255) | NOT NULL | 名称   |

### API 設計

<!-- API変更がある場合。ない場合は削除 -->

`POST /api/v1/resource`

リクエスト:

```json
{
  "field": "value"
}
```

レスポンス:

```json
{
  "success": true,
  "data": {}
}
```

### ロジック詳細

<!-- 主要な処理フローを箇条書きまたはステップで記述 -->

1. ユーザーが〜を実行
2. フロントエンドが〜を呼び出す
3. バックエンドが〜を処理
4. 結果を〜として返却

### エラーハンドリング

| ケース               | 期待する挙動                     |
| -------------------- | -------------------------------- |
| バリデーションエラー | 400 + エラーメッセージ表示       |
| 認証エラー           | 401 + ログイン画面へリダイレクト |
| サーバーエラー       | 500 + トーストで通知             |

## 実装タスク

<!-- チェックリスト形式で実装ステップを分解 -->

- [ ] タスク1: 〜を実装
- [ ] タスク2: 〜を実装
- [ ] タスク3: テストを追加

## 完了条件（Acceptance Criteria）

以下をすべて満たすこと:

- [ ] **機能**: （具体的な入力→出力の動作条件を記述）
- [ ] **バリデーション**: （入力制約・エラーケースの挙動）
- [ ] **テスト**: ユニットテスト追加済み（カバレッジ 80%+）
- [ ] **画面**:（画面変更がある場合）アスキーアート通りに表示される
- [ ] **パフォーマンス**: （必要に応じて応答時間等の基準）
- [ ] **レビュー**: コードレビュー承認済み
- [ ] **CI**: すべての CI チェックがパス

## 備考

<!-- 補足事項、制約、既知の問題、関連 Issue 番号など。
     外部リンクではなく、必要な情報はここに直接記述する -->
````

### アスキーアート作成ガイドライン

画面変更がある場合、以下のルールでアスキーアートを描く:

- **罫線文字**: `┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼ │ ─` を使用
- **幅**: 40〜60 文字程度
- **要素の表現**:
  - ボタン: `[ ボタン名 ]`
  - テキスト入力: `[________________]`
  - セレクトボックス: `[▼ 選択肢      ]`
  - チェックボックス: `[x]` / `[ ]`
  - テーブル: `│ col1 │ col2 │` 形式
  - タブ: `[ Tab1 | Tab2 | Tab3 ]`
  - アイコン: `(i)` `(!)` `(x)` `(+)`
  - スクロール: `▲ / ▼`
  - 省略: `...`
- **変更箇所**: `<<<NEW>>>` または `*** ここが変更 ***` で明示

---

## Step 4: ユーザー確認

生成した Issue 本文をユーザーに表示し、AskUserQuestion で確認する:

- **そのまま起票**
- **修正してから起票**（修正点を聞く）
- **キャンセル**

---

## Step 5: Issue 起票

ユーザー承認後、`gh` コマンドで起票する。

```bash
gh issue create \
  --title "[<種別ラベル>] <種別プレフィックス>: <タイトル>" \
  --body "$(cat <<'EOF'
<Step 3 で生成した本文>
EOF
)" \
  --label "<ラベル1>,<ラベル2>,..." \
  --repo <対象リポジトリ>
```

### タイトルフォーマット

`[<種別ラベル>] <プレフィックス>: <タイトル>`

| 種別        | ラベル        | プレフィックス | 例                                                   |
| ----------- | ------------- | -------------- | ---------------------------------------------------- |
| bug         | `bug`         | `fix`          | `[bug] fix: ログイン時に500エラー`                   |
| feature     | `feature`     | `feat`         | `[feature] feat: ユーザー一覧にページネーション追加` |
| improvement | `improvement` | `improve`      | `[improvement] improve: キャッシュ戦略の最適化`      |
| chore       | `chore`       | `chore`        | `[chore] chore: Node.js 22 へアップグレード`         |

---

## Step 6: 結果報告

起票完了後、以下を報告:

- Issue URL
- 付与したラベル一覧
- 次のアクション（`/issue-implement #<番号>` で実装開始できる旨）

---

## 注意事項

- ラベルが対象リポに存在しない場合は `gh label create` で作成してから起票する
- 画面変更がない Issue では「画面イメージ」セクションを省略する
- 完了条件は具体的・検証可能な内容にする（「〜すること」ではなく「〜が表示される」「〜が返却される」）
- Issue 本文に必要な情報を全て記載する。外部ドキュメントへのリンクで代替しない
- 詳細設計は「実装者が迷わない程度」の粒度でよい。厳密なフォーマット設計書にはしない
- コードベースを Grep / Read で調査し、影響範囲やファイルパスは実際のコードに基づいて記載する
